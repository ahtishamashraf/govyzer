# Data model

MySQL 8 compatible, created by JavaScript Knex migrations in `packages/database/migrations`.
Identifiers are 26-character ULIDs generated by the application, so ids are sortable and
non-enumerable. Money uses `DECIMAL(18,2)`; percentages use `DECIMAL(8,4)`.

## Conventions

- `organization_id` on every tenant-owned table, always indexed.
- `created_at` / `updated_at` on mutable tables; `deleted_at` for soft deletion.
- `created_by` / `updated_by` reference `organization_memberships.id`.
- `version` on records several people edit at once (optimistic concurrency).
- JSON is used only for provider payloads, configurable conditions, layouts and immutable
  snapshots — never for searchable business data.
- Append-only tables have `created_at` and no `updated_at`: `audit_logs`,
  `lead_stage_history`, `lead_assignment_history`, `unit_status_history`,
  `reservation_status_history`, `deal_stage_history`, `listing_price_history`,
  `listing_availability_history`, `unit_price_history`, `points_ledger`,
  `commission_snapshots`, `commission_lines`.

## Platform and access

`organizations`, `organization_domains`, `organization_branding`, `subscription_plans`,
`organization_subscriptions`, `feature_flags`, `branches`, `departments`, `teams`, `users`,
`organization_memberships`, `roles`, `permissions`, `role_permissions`, `membership_roles`,
`sessions`, `password_reset_tokens`, `email_verification_tokens`, `invitations`, `api_keys`,
`custom_field_definitions`, `custom_field_values`, `audit_logs`, `notification_preferences`,
`notifications`, `reference_sequences`.

A user may belong to several organizations: `users` is global, `organization_memberships`
is the tenant-scoped join carrying branch, team, manager, modules, record scope, capacity
and working hours.

## Contacts and CRM

`contacts`, `contact_identifiers`, `contact_roles`, `contact_addresses`, `contact_consents`,
`lead_sources`, `campaigns`, `tags`, `leads`, `lead_requirements`, `lead_tags`,
`lead_stage_definitions`, `lead_stage_history`, `lead_assignment_rules`, `lead_assignments`,
`lead_assignment_history`, `lead_sla_rules`, `lead_sla_events`, `lead_pool_entries`, `notes`,
`tasks`, `meetings`, `meeting_attendees`, `viewings`, `communication_threads`, `messages`,
`email_messages`, `call_logs`, `contact_merge_history`, `lead_merge_history`,
`external_lead_receipts`.

Key relationships:

- One **contact** holds many **roles** at once (buyer and landlord, for example) through
  `contact_roles`, and many **leads** at once through `leads.contact_id`.
- **Identity** lives in `contact_identifiers` with `(organization_id, identifier_type,
  value_normalized)` unique, which is what makes deduplication reliable while allowing the
  same number to exist in a different tenant.
- **Requirements** are separate rows so one lead can carry several simultaneous briefs.
- `external_lead_receipts` is the idempotency ledger for portal, webhook and API intake.

## Locations and inventory

`countries`, `administrative_areas`, `cities`, `communities`, `subcommunities`, `buildings`
(shared reference data, `organization_id = ''` for platform rows), then tenant inventory:
`developers`, `projects`, `project_phases`, `project_buildings`, `floors`, `unit_types`,
`units`, `unit_owners`, `unit_status_history`, `amenities`, `entity_amenities`,
`media_assets`, `floor_plans`, `brochures`, `price_lists`, `price_list_items`,
`unit_price_history`, `stock_releases`, `inventory_allocations`.

Three concepts stay separate on purpose:

| Concept | Table | Lifetime |
| --- | --- | --- |
| Unit | `units` | Permanent inventory |
| Listing | `listings` | Temporary marketing record for a unit or property |
| Portal publication | `portal_publications` | One listing on one portal, with its own status and error history |

## Ready listings and portals

`listings`, `listing_versions`, `listing_agents`, `listing_approvals`, `listing_permits`,
`listing_price_history`, `listing_availability_history`, `portal_providers`,
`portal_accounts`, `portal_field_mappings`, `portal_publications`, `portal_sync_jobs`,
`portal_sync_logs`, `portal_raw_payloads`.

Listing states: `draft → internal_review → approved → publishing → published |
partially_published`, plus `rejected`, `unpublished`, `expired`, `withdrawn`, `archived`.

## Off-plan

Reuses developers, projects, phases, buildings, unit types, units, media and price lists,
and adds `project_payment_plans`, `payment_plan_installments`, `unit_payment_plans`,
`unit_holds`, `reservations`, `reservation_extensions`, `reservation_status_history`,
`stock_import_batches`, `stock_import_rows`.

Unit stock statuses: `draft`, `unreleased`, `available`, `blocked`, `on_hold`, `reserved`,
`booked`, `sold`, `cancelled`, `withdrawn`, `unavailable`.

## Deals, documents and finance

`deals`, `deal_parties`, `deal_stage_history`, `deal_approvals`, `offers`, `bookings`,
`cancellations`, `document_templates`, `document_template_versions`, `generated_documents`,
`signature_requests`, `invoices`, `invoice_items`, `payments`, `payment_allocations`,
`receipts`, `refunds`, `commission_plans`, `commission_rules`,
`commission_plan_assignments`, `commission_snapshots`, `commission_lines`,
`commission_disbursements`.

`commission_snapshots` stores the rules and inputs used at the moment a deal was won, so
later plan edits never rewrite history. A cancellation writes a reversing snapshot rather
than mutating the original.

## Sales Screen

`sales_displays`, `display_pairing_codes` (hashed, single use, short lived),
`display_sessions`, `display_playlists`, `display_slides`, `display_widgets`,
`display_filters`, `sales_events`, `sales_event_approvals`, `points_rules`, `points_ledger`,
`targets`, `announcements`.

`sales_events.display_payload` holds only a display-safe projection; a sanitizer strips any
key resembling client PII before the row is written.
